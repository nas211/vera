# VELLA commercial integrations — disabled

VELLA is an Autonomous DeFi Trading Protocol. Financing supplies trading capital; it is not a separate user product. The initial implementation supports DogeOS Chikyū only. Future collateral adapters must identify chain, asset, decimals, custody/finality rules, oracle policy and lending liquidity explicitly. EVM, Solana and Bitcoin-backed collateral must not reuse each other's address/signature assumptions. Each adapter needs isolated ownership verification and reconciled accounting before it can be registered. No additional chain, asset or real lending adapter is enabled here.

`backend/autodefi/real_lending.py` defines a future liquidity interface and a constructor that fails closed. No liquid DogeOS lending market, stablecoin bridge, lender funding or real Lighter execution authorization is assumed to exist.

A real implementation must settle principal from actual, verified lender assets before recognizing a redeemable borrower balance. Pool NAV must distinguish cash, performing principal, collectible accrued interest, reserves and impaired/bad debt. Utilization is outstanding debt divided by cash plus performing debt; interest curves and protocol fees require explicit, reviewed policies. Lender shares represent actual NAV, with withdrawals constrained by available cash minus reserves and a disclosed queue when cash is insufficient. Reserve coverage, fee distributions and any loss waterfall must be explicit. Never value an unrecoverable loan at par or pretend a simulated USDC credit is a backed token.

Before enabling funds, verify DogeOS custody semantics and any lending/bridge counterparties, stablecoin contracts, finality, asset decimals, fees and withdrawal liquidity. A production oracle needs multiple independent sources, stale-price and divergence checks, confidence bounds, circuit breakers and reviewed sequencer/finality assumptions. The illustrative price in this prototype is categorically insufficient.

Liquidation requires funded keepers, bounded close factors, collateral seizure ceilings, incentives, slippage limits and solvency-aware auctions. A paused or missing oracle must block borrowing and risky withdrawals without fabricating prices; define debt accrual, emergency resolution and lender loss treatment during prolonged outages. Test liquidity exhaustion, correlated DOGE/trading losses, negative execution equity, full collateral seizure and persistent bad debt. Stopping trading alone does not prevent collateral liquidation.

Lighter execution would require independently authorized execution credentials, segregated per-user funds, enforceable off-chain limits, exchange reconciliation and verified deposit/withdrawal settlement. On-chain permissions cannot enforce an external venue that bypasses the contracts. The AI must remain unable to transfer collateral or override deterministic checks.

Contracts in this prototype are immutable, with no upgrade proxy. Production changes require an independently reviewed migration and explicit owner consent. Audit contracts, signature boundaries, attestor trust, oracle design and loan/paper reconciliation before deployment. Define monitoring for chain reorgs, stalled receipts, duplicate engine writers, ledger divergence, stale orderbooks, model failure, fee drift and solvency. Revenue could come from disclosed interest spreads, protocol fees or performance fees only after loss treatment and applicable obligations are reviewed; no revenue or return is guaranteed.
